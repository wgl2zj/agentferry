# UI_DESIGN.md — UI 设计与前端体验规范

> 本文件是项目 UI 设计规则的唯一权威源。由 `AGENTS.md`（AI 执行规则）路由后生效，适用于新增或修改模板、样式、浏览器交互和用户可见文案的任务。

## 一、适用范围与业务边界

- 【强制】修改页面模板、样式表或用户可见的浏览器脚本时，完整加载本文件；同时执行 `.rules/CODING_STANDARDS.md`（编码与测试规则）。
- 【强制】UI 改造只调整展示与交互层，不改变业务计算逻辑、状态机、数据库业务数据、权限模型或生产部署方式。
- 【强制】明确项目的支持视口范围并写入本节（示例：桌面端专用系统可定最低支持视口 1024×768，不设计、不实现、不验证移动端布局）；低于支持范围的布局不属于 UI 支持范围。
- 【应当】先公共层、后页面族；先可达可读、后视觉美化；不得在公共层能够解决时复制页面级样式。

## 二、设计令牌

### 2.1 唯一来源

- 【强制】全站设计令牌（颜色/间距/圆角/阴影等设计变量）定义在 `src/styles/tokens.css` 的根作用域中。
- 【强制】业务模板和其他样式文件使用令牌变量，不得新增原始十六进制、`rgb()` 或 `hsl()` 颜色值；数据可视化确需动态色板时，在设计令牌文件集中定义并写明语义。
- 【强制】颜色必须表达语义，不以页面或人员命名。状态统一为：中性、进行中、成功、警告、危险。

### 2.2 固定尺度

| 类别 | 允许值（示例，可按项目调整，但必须固定成有限集合） |
|---|---|
| 间距 | 4、8、12、16、24、32px |
| 控件圆角 | 6px |
| 卡片/浮层圆角 | 12px |
| 阴影 | 卡片阴影、浮层阴影两档令牌 |
| 普通控件高度 | 至少 44px |
| 密集表格行操作 | 至少 32px，且必须有可访问名称 |

- 【强制】正常文本与背景对比度不低于 4.5:1；大号文本不低于 3:1。
- 【强制】黄色、青色等浅色背景不得搭配低对比度白字。

## 三、页面骨架与信息层级

### 3.1 标准顺序

完整业务页面按以下顺序组织：

1. 页面头：唯一可见 `h1`（页面一级标题）、一句说明、主操作。
2. 工作上下文条：当前任务条件（如业务周期、批次、状态、锁定或异常等）。
3. 筛选条：字段、已选条件、结果数和清除入口。
4. 数据区：表格、卡片、表单或步骤流。
5. 空/错状态：原因、下一步、主操作和帮助。
6. 分页或固定操作条。

- 【强制】每个完整页面恰好一个可见 `h1`（页面一级标题），标题层级连续，不用字号代替语义层级。
- 【强制】同一页面只有一个视觉主操作；危险操作不得与主操作使用相同层级。
- 【应当】首屏优先显示当前任务、阻断原因和下一步，不重复展示同一数字或同一入口。

### 3.2 导航

- 【强制】品牌和一级模块保持单行；一级模块使用按钮，只展开对应二级菜单且不触发页面跳转，实际页面导航统一由二级菜单链接承担。
- 【强制】权限过滤后不得显示空业务分组；长用户名不得覆盖品牌或菜单按钮。

## 四、响应式与数据表格

### 4.1 视口基线

- 【强制】前端改动至少验证项目声明的最小视口与两种常见视口（示例：1440×1000、1366×900、1024×768）。
- 【强制】页面文档不得产生横向滚动；宽数据只能在独立表格容器内横向滚动。
- 【强制】不得使用 `overflow-x: hidden`（隐藏横向溢出）掩盖数据不可达问题。

### 4.2 宽表规则

- 【强制】宽表使用统一表格壳层和局部滚动容器，所有数据列与操作列均可到达。
- 【强制】表头可固定；数字右对齐；名称和说明左对齐；短状态与短枚举居中。
- 【强制】涨跌/增减同时显示正负号和方向文字或图标，不得只依赖颜色。
- 【应当】单行最多保留一个直接动作和一个"更多"菜单；高密度页面提供批量操作、分页和列显示设置。
- 【强制】首列冻结和多层固定表头必须验证层叠顺序，不得遮挡可滚动内容或参考行。

## 五、组件与状态语言

### 5.1 公共组件

- 【强制】优先复用公共组件：页面头、工作上下文、筛选条、状态标签、空状态、表格壳层、Toast（轻量反馈）、确认对话框、任务进度、详情抽屉。
- 【强制】新增公共组件先在至少三个代表页面验证可复用性，再扩大迁移；不得创建只换名字的页面专用副本。

### 5.2 状态与反馈

- 【强制】成功和轻量失败使用 Toast 或行内反馈；需要用户修正的错误紧邻字段或操作区域。
- 【强制】不得新增浏览器原生 `alert()`（提示）、`confirm()`（确认）或 `prompt()`（输入）；遗留调用按页面族迁移。
- 【强制】删除、恢复、发布、覆盖等高风险动作使用统一确认对话框，持续显示对象、影响和操作后的目标状态。
- 【强制】数据恢复、永久删除等不可逆动作要求二次输入确认。
- 【强制】超过 1 秒的操作显示加载状态；长任务显示阶段、进度、失败项和结果入口，不用无限旋转替代真实进度。
- 【强制】空状态必须说明"为什么为空"和"下一步做什么"，不得只显示"暂无数据"。

### 5.3 消息通道矩阵

- 【强制】用户可见提示统一归入四类通道：顶部横幅（页面顶端）、右上角 Toast（轻量浮出）、居中弹窗（确认/输入对话框）、行内提示（紧邻字段或操作区域）；不得新增第五类提示位置或第二套同位置机制。
- 【强制】重要/轻量判定：改变业务数据或状态的操作结果、需要用户介入处理的失败、需要用户阅读的汇总信息为重要结果；不改变数据的界面反馈和自动行为提示为轻量反馈。
- 【强制】顶部横幅用于整页提交或跳转后的重要结果，持久显示至手动关闭，不得用于轻量反馈。
- 【强制】右上角 Toast 用于轻量反馈：成功/提示类数秒自动消失；警告/错误类不自动消失、必须手动关闭；相同内容的 Toast 不重复堆叠。
- 【强制】居中弹窗只承担"做决定"（确认、输入）或展示需用户阅读的重要结果，不得用于轻量反馈。
- 【强制】同一操作的结果只在一个通道出现一次；刷新页面的操作不得"先 Toast 后横幅"双重提示。
- 【强制】全局未捕获的网络错误统一走 Toast（危险类、手动关闭），不得另设浮条机制。
- 【强制】表单校验提醒（如"请先选择行""内容不能为空"）优先行内提示或字段旁反馈，不占用横幅。

## 六、表单、图标和文案

- 【强制】每个表单控件都有可见标签或等价的可访问名称；占位符不能代替标签。
- 【强制】图标统一使用一套已加载的图标库；不得使用未加载的图标类。
- 【强制】纯装饰图标使用 `aria-hidden="true"`（辅助技术隐藏）；纯图标按钮必须提供可访问名称（`aria-label`）或可见文字。
- 【强制】弹窗关闭按钮使用可访问名称；成功、失败、警告和确认文案说明对象及后果。
- 【强制】业务界面不显示数据库主键、源码文件名、内部字典名等技术细节；确需保留时进入日志或开发详情。
- 【应当】页面标题使用"对象 + 任务"结构，按钮使用明确动词，避免"确定""处理"等脱离上下文的泛化文案。

## 七、可访问性与动效

- 【强制】键盘焦点始终可见，交互顺序与视觉顺序一致；菜单、抽屉、弹窗和表格操作可仅用键盘完成。
- 【强制】弹窗打开后焦点进入弹窗，关闭后归还触发器；不得让焦点落到被遮挡内容。
- 【强制】状态、涨跌、选中和错误不得只依赖颜色表达。
- 【强制】自定义动画遵守 `prefers-reduced-motion`（减少动态效果偏好）。
- 【应当】装饰性动画控制在 300ms 内，不给常规卡片增加位移式悬浮效果。

## 八、复杂业务页面族

- 【强制】同一业务流程的多个工作台页面使用一致的导航与上下文条，当前位置始终可见。
- 【强制】只抽取页面族上下文、状态栏、工具条、抽屉、确认对话框等展示交互层，不重写业务服务（保存、流转、审批、发布等）。

## 九、实施与验证纪律

- 【强制】新增页面或页面族迁移前，先确定所用公共组件和设计令牌；无法复用时记录原因。
- 【强制】UI 治理检查脚本尚未建立；建立前以本文件「UI 任务完成清单」逐项人工核对代替，未逐项核对不得汇报完成。
- 【强制】使用本地临时测试目录（构造假的 agent 资产目录树）执行前端 E2E，不得访问真实家目录下的资产。
- 【强制】浏览器检查记录目标视口、页面级横向溢出、表格列可达性、控制台错误、键盘焦点、空状态和错误状态。
- 【强制】公共骨架、权限导航、核心流程或公共反馈组件改动后，只建议用户决定是否运行全量回归，不得自主执行。

## 十、UI 任务完成清单

- [ ] 页面符合标准骨架，且恰好一个可见页面一级标题。
- [ ] 项目声明的目标视口已验证，页面无横向滚动，宽表所有列可达。
- [ ] 主操作、危险操作、状态、空状态、加载和失败反馈符合统一语义。
- [ ] 提示信息符合消息通道矩阵：通道归类正确，同一操作结果只出现一次，无"先 Toast 后横幅"双重提示。
- [ ] 表单、图标、弹窗、抽屉和菜单具备可访问名称、焦点管理和键盘路径。
- [ ] 未新增原始颜色、原生弹窗、未加载图标类、隐藏横向溢出或页面专用重复组件。
- [ ] 未改变业务计算、状态机、权限、数据库和生产部署等业务边界。
- [ ] UI 治理检查、直接相关测试和本地浏览器验证通过；未覆盖状态已明确说明。
- [ ] 临时截图、追踪、日志和测试目录未进入提交。
